# ZenGear Web

Next.js with TypeScript, Tailwind CSS, shadcn/ui, TanStack Query, Zustand, React Hook Form + Zod, next-intl, Firebase JS SDK — hosted on Vercel (Root Directory `web`). Read `../docs/FRONTEND.md` before adding code and `../docs/SCREENS.md` for the screens. All commands below run from `web/`. Decision: DEC-104, DEC-116, DEC-118.

## Rules that must not be broken

- Code lives in a module, `src/features/<area>/<module>/` (`api/`, `components/`, `hooks/`, `utils/`, `schemas.ts`, `index.ts`), or in `src/features/shell/<module>/` for the frame of the admin and the POS, and moves to a shared folder (`components/app`, `hooks`, `utils`, `lib`) only once two modules use it. `app/` holds routes only and imports a module through its `index.ts`; a module imports another only through its `index.ts`, and a module that others import exports no screen; shared folders import neither `features/` nor `app/` (DEC-118 (1), (2); ESLint refuses the rest). A screen is a layout of slots, sections that hold data and behavior, and presentational components (DEC-118 (3)); keep a new file, or a file whose content changed (not counting a move or changed imports), at most 150 lines of code (the `max-lines` warning). Details: `../docs/FRONTEND.md`, *Modules and boundaries* and *Screens in three layers*.
- API types come only from `src/lib/api/schema.d.ts`, generated from `../api/openapi/ZenGear.Api.json` with openapi-typescript. Never edit it and never hand-write a type the API already describes. After any API change: regenerate, fix type errors, commit both together.
- All HTTP calls go through the one typed client in `src/lib/api/` (openapi-fetch; the instance is `src/lib/api/api.ts`). It adds the Firebase ID token to every call but those of `/api/v1/shop/`; the caller passes `If-Match` for edits (`etagOf` of `src/lib/api/concurrency.ts`, a typed header parameter of the contract) and `Idempotency-Key` for checkout and payments (`newIdempotencyKey`) (`../docs/API_CONVENTIONS.md`).
- Server data lives in TanStack Query; Zustand only for client state (cart drawer, POS screen state). Never copy server data into Zustand.
- The API decides prices, totals, stock, permissions and status transitions. Show what the API returns; Zod schemas only check input shape before sending.
- Errors are Problem Details whose texts the API writes (DEC-117 (4)): show the `detail` of each `errors` item under the field its `pointer` or `parameter` names (the others at the top of the form), and the problem's `detail` in a toast or on the page; never map a `type`, `code` or status to a text of your own (only `problems.network` and `problems.unknown` are the web's, and Firebase `auth/*` codes); `type` and `code` only choose a behaviour; `ruleId` is for logs, not for display.
- Money is integer VND, formatted with `Intl.NumberFormat`; dates are shown in Asia/Ho_Chi_Minh with `Intl.DateTimeFormat`; both with the locale of next-intl (`src/i18n/config.ts`, DEC-118 (4)); `date-fns` (with the locale `vi` of `date-fns/locale`) serves only the calendar and the date pickers, never with its time zones (DEC-116 (6)).
- Every text the user sees goes through next-intl (`t('key')`) from `messages/vi.json`, never written in JSX, except the texts of the errors the API answers (DEC-117 (4)); the labels of business terms are the Vietnamese terms of `../docs/GLOSSARY.md`; code uses its English entity names. Phase 1 ships Vietnamese only; English comes later for the storefront only.
- `src/components/ui/` is code of the app (open code, DEC-116 (1)): add a component with `npm exec --no -- shadcn add` (the CLI pinned in `package.json`, DEC-111 (2); never `npx shadcn@latest`), commit what it wrote alone (`/implement-feature` step 7, `/fix-defect` step 5), then edit it like other code. Keep shadcn's design: the classes that set a component's look (colour, spacing, radius, font size, shadow) change only to fix accessibility; theme with the CSS variables of `src/app/globals.css` and `components.json`, and a new variant uses the theme's tokens. A component in `src/components/app/` or `src/features/<area>/<module>/` composes several of them. A block of `@shadcn` is a template: its files move to `src/features/<area>/<module>/` or `src/components/app/`, without its sample page, data and texts (DEC-116 (3)). An update of a component is a `chore(web)` pull request of its own, never part of a feature: `add --overwrite` only when none of the files it writes was edited, otherwise the registry's changes by hand; never `--all` or `--path` (DEC-116 (4)). Only the official registry; a third-party one needs a Decision (DEC-116 (7)).
- A package is added only when `approved-packages.json` lists it, with an exact version (DEC-104, DEC-111 (3); `tools/pr_gates.py` checks both and the lockfile). A package that an official installer of an approved package adds (`shadcn add` of an official item, the install command in the documentation of an approved package) and the list does not hold is approved first by a pull request of its own that the owner merges (DEC-111 (5); `/implement-feature`, step 4); any other package needs a Decision first. The shadcn CLI may add the packages of an official component that the list already holds.
- Every official shadcn item may be used, also one that writes English: in the pull request of its `add`, every text a user reads or a screen reader reads in its source goes through `t(key)` of the namespace `ui` (ESLint checks `src/components/ui/` too), and a text its package shows (the labels of `sonner`, the navigation labels and month names of react-day-picker, the default texts of cmdk and vaul) is set through the package's prop or locale from the message files, which `code-reviewer` checks (DEC-116 (2)). No item that needs `@base-ui/react` or `@shadcn/react`.
- Icons are named imports from `lucide-react`, and a block that imports another icon set is switched to them (`@tabler/icons-react` is not approved, DEC-116 (3)); animation uses `motion` with `MotionConfig reducedMotion="user"`, and stays minimal in the admin and the POS.
- Hiding a button is not authorization. Admin and POS pages still rely on the API returning 401/403; the client layout (on SCR-AUT-02 the section that holds the session, `ChangePasswordSession`) redirects a visitor without a session, and `src/proxy.ts` only makes fixed route redirects and sets the CSP with a nonce of `/admin` and `/pos` (DEC-113 (5)); it never reads or checks the session. The root layout of `/admin` (and of `/pos` when it comes) keeps `await connection()`, so that no page there renders statically, and a catch-all page under it calls `notFound()`, so that an unknown URL renders with the nonce too (DEC-114 (2); `/pos` gets its own with its first screen); a script added there needs the nonce (`docs/FRONTEND.md`, *Security headers*).
- No secrets in code or in `NEXT_PUBLIC_*` variables; only the public Firebase web config may be public. `src/env-schema.ts` checks them (Zod); outside a production build the values of the development environment are its defaults, so no env file is needed for `npm run dev`.

## Commands

Node.js is the version of `.nvmrc` (`npm ci` refuses a Node.js outside the `engines` range of `package.json`, `engine-strict`); use the npm bundled with it, and run `npm ci` again whenever `package-lock.json` changed. The scripts call the same commands as the CI job `web-test`, which runs the binaries through `npm exec --no --`.

- Dev server: `npm run dev` (http://localhost:3000/admin, after `tools/dev_reset.ps1` and the API on the launch profile `http`)
- Regenerate API types: `npm run gen:api`
- Checks before commit: `npm run lint` (`eslint .`) · `npm run format` (`prettier --check .`; fix with `npm exec --no -- prettier --write <files>`) · `npm run typecheck` (`next typegen && tsc --noEmit`) · `npm run test` (`vitest run`) · `npm run build` (`next build`, a production build: it reads the five `NEXT_PUBLIC_*` values from the environment and has no defaults, so set them first, in a terminal of its own since they stay set there: any valid values pass, for example the development ones of `src/env-schema.ts` (in PowerShell `$env:NEXT_PUBLIC_API_BASE_URL = 'http://localhost:5256'` and the four others; CI uses those of the `env` of `web-test` in `../.github/workflows/pipeline.yml`))
- Screen flows: `npm run e2e` (Playwright, `e2e/`) against the development environment (`../docs/ACCEPTANCE.md`); CI runs them in the job `acceptance` against the API image and the Firebase Auth Emulator
