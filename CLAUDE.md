# ZenGear

Retail system for a PC and hardware store run as a Vietnamese household business (hộ kinh doanh): storefront, admin, POS, inventory ledger, purchasing, warranty and returns, cash book.

## Repository

| Folder | Content | Own rules |
|---|---|---|
| `api/` | .NET 10 backend: `ZenGear.Api` → `ZenGear.Services` → `ZenGear.Data`, tests, `db/` (schema specification), `seed/`, `openapi/` (generated) | `api/CLAUDE.md` |
| `web/` | Next.js app: storefront, admin, POS | `web/CLAUDE.md` |
| `docs/` | Specifications shared by both | — |
| `tools/` | Blueprint export, schema snapshot | — |

Decision: DEC-093 (monorepo), DEC-091 (3-Layer backend).

## Rules for every change

- Code follows the specifications. If a rule is ambiguous or code needs a different design, stop and propose a Decision; never change the blueprint, `docs/DATABASE.md` or `api/db/` silently.
- Use the names in `docs/GLOSSARY.md`; add a row there before introducing a new business term.
- The API contract is `api/openapi/ZenGear.Api.json`, generated by building `ZenGear.Api`. An API change and the matching web change go in the same commit; the web never hand-writes API types.
- Business rules are enforced by the API. The web may validate input for a better experience but never decides prices, stock, permissions or status transitions.
- Money is integer VND; timestamps UTC; day-based logic and display in Asia/Ho_Chi_Minh.
- Never log or commit secrets, tokens, passwords or OTP codes. Personal data columns are listed in `docs/DATABASE.md` (Conventions → Personal data).

## Local environment

`api/docker-compose.yml` (Visual Studio Docker Compose project) runs PostgreSQL 18 and Redis; launch profile `Infrastructure` starts only these two, and the API runs from its own project. Firebase runs with the Firebase Local Emulator Suite. Setup order for the database is in `api/CLAUDE.md`.

## Commits

Every commit follows Conventional Commits 1.0.0, in English:

```
<type>(<scope>): <subject>

<body>

<footer>
```

- `type`: `feat` (new behavior), `fix` (bug fix), `docs`, `refactor` (no behavior change), `perf`, `test`, `build` (packages, SDK, project files), `ci`, `chore` (other tooling), `revert`.
- `scope`: `api`, `web`, `db` (schema specification and migrations), `seed`, `docs`, `ci`. Omit the scope when a change spans several of them.
- `subject`: imperative, lowercase, no final period, at most 72 characters (aim for 50).
- `body`: what changed and why, wrapped at 72 characters; group by project when several are touched.
- `footer`: `Refs: <Feature ID>, <Rule ID>, <DEC-xxx>` for the blueprint items the commit implements or changes; `BREAKING CHANGE: <description>` (or `!` after the type) when an API contract or schema change breaks existing callers or data.
- One logical change per commit. An API change and its web change stay in one commit (`feat: …` without scope).
- Pull request title: the same format as a commit subject, with the feature ID at the end in parentheses (`feat(api): add role-based access control (AUT-04)`); merge with **Rebase and merge** so every commit keeps its message. Checked by `.githooks/commit-msg` (enable once per clone: `git config core.hooksPath .githooks`) and by the `pr-title` workflow.
- No secret in any commit: `.githooks/pre-commit` scans the staged changes with gitleaks (warns only if gitleaks is not installed) and the `secrets` workflow scans every pull request; an allowlist entry in `.gitleaks.toml` needs the user's approval and a comment saying why. Never commit with `--no-verify`.

## Workflow

- One branch per feature from `main` (`feat/aut-04`); never work on `main` except for `docs` commits.
- `/implement-feature <ID>` plans (reviewed by the `plan-reviewer` agent), tests and builds; `/finish-feature <ID>` verifies, proposes the commits and the pull request.
- Claude Code never pushes or merges; the user does. Edits to `api/db/`, `docs/blueprint/`, `docs/DATABASE.md` and the blueprint workbook ask for confirmation (`.claude/hooks/guard-spec.ps1`); change them only with the Edit or Write tools, never with shell commands, and never work around the confirmation.
- `/check-docs` reports inconsistencies between the documentation, the code and CI.
